# RELYR stability contract

Read this before changing input, Deck layout, startup, shutdown, or installer code. It is the short routing map for future work; `AGENTS.md` and `docs/modifier-click-contract.md` remain authoritative.

## Non-negotiable behavior

- Shift+left-click and Ctrl+left-click support both short clicks and drags. PowerPoint Ctrl-drag copy is a required case.
- Generated order is `modifier Down -> left Down -> left Up -> modifier Up`.
- Modifier Start/End, native right-drag output, and taskbar short-click replay run on dedicated workers. Never inject input synchronously from a low-level hook callback or while it owns `InputEngine.stateLock`.
- A taskbar short click whose physical Down/Up was suppressed is a restoration event, not a cancelable action. Its replay must never be removed by settings apply, emergency stop, engine disable, session transition, or shutdown cleanup, and its synthetic Down/Up must be submitted as one atomic output batch.
- A suppressed short `Taskbar+MouseRight` restores the original right-button Down/Up as one atomic synthetic input batch only after the originating low-level hook callback has returned. The hook thread never waits. Do not post `WM_CONTEXTMENU` directly to a taskbar child window: Windows 11 app icons require Explorer's normal pointer-input route, and a queued message does not prove that the app-icon menu opened.
- If an atomic taskbar click replay is incomplete or throws, defensively release every generated mouse button and disable RELYR input interception for the rest of that process. Internal failure must fail open to ordinary Windows input; it must never leave the taskbar or desktop persistently unclickable.
- Physical movement stays suppressed until `NotifyNativeMouseDragStarted` confirms modifier Down plus synthetic left Down.
- Raw Input tracks physical buttons independently and recovers a missing low-level Up.
- Normal-layer MouseLeft remains protected. `Taskbar+MouseLeft` is permanently reserved in full so Windows retains both ordinary clicks and pinned-app icon drag/reorder; neither TAP nor HOLD may be assigned or intercepted. `Taskbar+MouseRight` TAP remains reserved for Windows while HOLD may be assigned, and its native short click is restored atomically. An applicable taskbar right-button long-press mapping takes priority over a normal mouse layer.
- Every assignment mutation route (direct edit, Action drop, single/multi paste, move, all-layer, all-profile, import, and migration) applies the same input policy before replacing an existing mapping. Rejecting a reserved TAP must never erase an existing HOLD or report a successful assignment.
- Single-key and multi-selection context menus expose assignment to all layers/profiles and removal from all layers/profiles. A multi-selection scope command applies to every selected input as one editor-history transaction, so one Undo restores the complete batch. Deck selection does not expose layer/profile scope commands.
- Space, CapsLock, mouse layers, Deck close, single-instance ownership, and graceful installer shutdown are regression-protected.
- Cursor locking is stored on each gesture definition. The selected gesture exposes that switch in its editor header; the general settings screen exposes only gesture sensitivity. A gesture snapshots its cursor behavior when it starts so switching or editing definitions cannot change an active gesture midway.
- While one gesture source remains physically held, every move-stop segment may execute its direction Action, including repeated segments in the same direction. Releasing the source commits any final pending segment before clearing its suppression marker, so the next fresh short press executes the Center Action on its first press rather than being consumed as stale gesture cleanup.
- Deck buttons remain 54x52. The visible horizontal button gap equals the vertical button-to-button distance, including the name-label area. Names must remain visible.

## Regression prevention contract

Every change must preserve already-working behavior. A feature request does not authorize redesigning an unrelated subsystem or changing an existing specification as a side effect.

- Change one execution path at a time. An input fix must not alter Deck state, a Deck fix must not alter hooks or runtime integrity, and a visual change must not alter profile routing unless the request explicitly requires it.
- Treat a reported failure as a regression first. Identify the last known-good artifact/source and the first bad change before adding a new recovery mechanism or special case.
- Prefer reverting the change that introduced the regression. Do not add foreground-app exceptions, own-process exceptions, fallback input paths, or action-specific workarounds unless the specification explicitly requires them.
- The visible RELYR main window is an ordinary application surface. It must run at ordinary user integrity and accept the same normal-profile keyboard and mouse layer input as Notepad, Word, Chrome, Filmora, and other applications. Only privileged operations use the elevated helper.
- RELYR foreground state, focus, text fields, Deck editing mode, and the selected layer editor page must not disable standard, Space, CapsLock, MouseRight, MouseBack, or MouseForward layer processing.
- A user-managed input-disabled application is the only foreground-app exception. While an exact registered executable is active, both keyboard and mouse hooks pass every physical input through without mappings, layers, replay, or synthetic output. A press captured before the foreground transition remains owned only until its matching physical release, preventing stuck keys or buttons; leaving the app restores normal processing automatically.
- Automatic profile routing follows only the foreground application. Moving the pointer over an inactive application must not change the runtime profile. RELYR's main window and owned management dialogs are ordinary foreground application surfaces, resolving to a specifically assigned RELYR profile or otherwise the standard profile.
- A close action targeting the window under the cursor requests activation and immediately posts `SC_CLOSE` to the same already-resolved target without waiting for foreground acknowledgement. An inactive target must receive the close request on the first invocation, and the action must never be discarded or fall back to another window.
- Window-under-cursor move, snap, minimize, maximize, restore, close, and virtual-desktop actions must reject Explorer shell surfaces such as `Progman`, `WorkerW`, and primary or secondary taskbars. Ordinary Explorer folder windows remain valid targets. A shell surface must never be resized, moved, hidden, or closed because doing so can remove a monitor's wallpaper and desktop hit target until Explorer restarts.
- The shell-surface guard applies to destructive window operations, not ordinary generated keyboard input. Visible Explorer desktop hosts (`Progman` and `WorkerW`) are valid destinations for mapped keys and shortcuts so remapped Delete, Ctrl+V, gestures, and layer actions still reach desktop icons. Primary/secondary taskbars and transient shell surfaces remain invalid cursor targets, and `Progman`/`WorkerW` remain invalid for move, resize, minimize, maximize, hide, close, and virtual-desktop window operations.
- For a `Taskbar+...` mapping, the taskbar is the invocation surface and never the action target. Direct taskbar key and shortcut actions use the existing active window and must not resolve the Explorer taskbar through the window-under-cursor path. This separation must not weaken the shell-surface rejection used by window actions.
- Key and shortcut actions targeting the window under the cursor activate that resolved window immediately before `SendInput`. This includes keyboard and wheel zoom shortcuts. Activation failure must never fall back to the previously active window.
- A virtual-desktop action queued from a low-level callback must not begin until that originating callback has returned. The output worker waits on the callback-return barrier; the hook thread never waits on the desktop worker. This preserves the matching mouse-button Up and prevents a layer from retaining normal clicks across a desktop change.
- While MouseRight, MouseBack, or MouseForward is held as a layer, an unassigned child mouse button remains an ordinary Windows click. It must not create a qualified `PressState`; releasing the layer before the child button must never retain or suppress later clicks.
- MouseRight wheel/tilt assignments must not disable an application's native right-button drag. When movement crosses the drag threshold, the worker emits right-button Down followed by the triggering movement before later physical movement is passed through. A later mapped wheel/tilt action may end that drag, but must never leave an unmatched right button or open a context menu.
- The Deck editor and the live Deck overlay use the same `DeckLayoutDefinition` objects. Runtime-profile selection may use a snapshot, but `DeckLayouts` and `SharedDeckMappings` must not be deep-cloned or allowed to diverge.
- Deck post-action and pointer-leave display behaviors are edited in the Deck workspace, remain global preferences shared by all Deck layouts, and must survive saving the general settings dialog unchanged. Each trigger independently supports stay visible, collapse to an edge tab, or fully hide. A pinned Deck suppresses either automatic transition; legacy boolean settings migrate `true` to collapse and `false` to stay visible.
- Different Deck layouts may be visible at the same time. Each Deck owns independent expanded and collapsed positions, size, pin state, and auto-hide lifecycle; toggling or refreshing one Deck must not hide, rebuild, or move another.
- A file, name, icon, color, assignment, reorder, deletion, row/column change, or profile-linked Deck change made in either the editor or overlay must appear in the other immediately and persist across restart.
- A one-slot Deck change (file drop, deletion, name, icon, color, monitor, or assignment) refreshes only that slot in the editor and every visible overlay. A reorder refreshes only its source and destination. Auto Save after either operation must not turn the differential update into a full Deck rebuild; full rebuilds are reserved for structural layout/profile replacement.
- Deck assignment clipboards survive profile switches. Clearing an icon must rebuild the ordinary button visual without retaining the icon font, animation, or transform.
- Moving an auto-hidden Deck to its edge tab must not interpret a stationary pointer as a fresh hover. Synthetic `MouseEnter`/`MouseLeave` raised while applying the collapsed bounds are ignored; the tab expands only after the pointer has genuinely left and re-entered, so it cannot oscillate between collapsed and expanded bounds.
- Entering an edge tab does not count as entering the restored expanded Deck. When the saved expanded position is away from the tab, the Deck stays open while the pointer travels to it; pointer-leave auto-hide becomes eligible only after the pointer has genuinely entered the expanded Deck.
- Entering a collapsed Deck through its right-edge move handle preserves drag initiation, but continuing from the handle into the tab body must re-run expansion because the parent window does not receive a second `MouseEnter`.
- Interactive Deck resize ignores the initial rounding-only pointer frames, selects one driving axis after meaningful movement, and keeps it for the complete sizing session. Width and height must change monotonically without alternating corrections. The WPF panel clip is updated once per panel-size change and the native rounded region is refreshed once on release rather than on every sizing frame.
- The Deck overlay itself is an opaque native window (`AllowsTransparency=false`) with a native rounded region; it must never create an invisible transparent hit-test surface over another application.
- Fully hiding a Deck removes its native window from display and releases every Deck-owned mouse capture. It must not leave an edge tab, transparent window, or any other hit-test surface. Collapsing is a separate state and leaves only the bounded visible edge tab.
- Interactive Deck and keypad overlays use bounded opaque native windows. Pure notification, thumbnail, and drag-preview windows may use transparency only when both WPF hit-testing and the native extended window style make their separate top-level HWNDs click-through (`WS_EX_TRANSPARENT | WS_EX_TOOLWINDOW | WS_EX_NOACTIVATE`).
- A collapsed Deck is a small normal-state native window, never a maximized or expanded hit-test surface. Pin, reset, overflow, and close controls are hidden while collapsed; only the right-edge move handle is interactive. Its dragged position persists across expansion, re-collapse, profile refresh, and restart, while moving it must not change the separate bounds restored on expansion.
- A collapsed Deck may be dragged across the complete virtual desktop, including monitors above, below, or beside the primary display. Primary-monitor work-area clamping must never pull it back across a monitor boundary.
- Deck maximize fills the current monitor work area in a normal opaque window, scales the button grid uniformly, and restores the exact prior position and size. The temporary maximized bounds must never overwrite the saved Deck geometry. The maximize/restore control is distinct from resetting the Deck to its initial fitted size.
- The Deck editor keeps its command bar stable while dimensions change. Its default body belongs entirely to the Deck preview; settings appear only on demand in one `Deckをカスタマイズ` drawer with Layout, Appearance, and Behavior tabs. The drawer occupies a bounded column between preview and inspector when wide and stacks above the preview with hysteresis when narrow. Closing it returns all body space to the preview. The Deck name is a plain inline-editable heading, the application-level Save action stays in the top toolbar, and compact widths replace secondary command labels with tooltip- and automation-named icons rather than wrapping or clipping them. The preview uniformly scales the complete configured grid through 18x18 so no outer row or column is cut by the settings drawer; list view provides the larger scrollable per-button editing surface. Column, row, padding, and corner-radius Sliders update the editor and visible overlay on each rendered value without writing a stale value back into the captured Thumb. Dimension changes retain existing cells and touch only the added or removed tail; appearance changes do not rebuild button content. Auto Save waits until the Slider releases and must not trigger a full 324-cell rebuild during a drag.
- The Deck editor provides two equivalent views of every visible slot. Grid view reflects the actual Deck rows and columns; list view remains vertically scrollable and shows every slot, including unassigned slots, with the Deck button on the left and its current Action summary on the right. Selecting, editing, recoloring, renaming, assigning, or reordering a slot through either view updates the same `DeckLayoutDefinition` and the live overlay.
- A selected keyboard key and a selected Deck button use the same read-only Action summary in the inspector. Keyboard summaries show `TAP` and `HOLD`; Deck summaries show one `ACTION`. Replacing an Action always uses the shared Action-library drag route, including Deck editing, and must not reveal the retired direct Action form. Parameterized text and launch/path rows request their concrete value only after a valid drop.
- The main window keeps the left navigation narrower than the right inspector at every responsive breakpoint. Their fixed labels remain on one complete line, and supporting controls reflow vertically instead of widening either pane or clipping text. Width removed from either supporting pane belongs to the central work area. The frame-free right inspector keeps the established centered launcher position for the Action library. The library replaces the same pane instead of adding another column or widening it, and all fixed row text stays on one line. One blank editor click closes it, while key, Deck, and interactive-control clicks remain available. Its whole-row drag preview is a separate transient click-through tool window only; while a key is the active drop target, that preview must remain completely outside the key's screen rectangle so both short- and long-press halves stay visible, including at monitor edges. Menu and drop animations reuse in-window, non-hit-test visual layers and never add an input-blocking surface. Context hints appear only for supported interactions and disappear while an assignment editor or the Action library is open.
- The Action library begins with one compact full-width category selector. Its popup starts with `お気に入り`, `最近使ったもの`, `すべて`, and `使用中`, groups the remaining categories under quiet headings, and uses the available right-pane height instead of a fixed truncated height; low-resolution panes clamp it to their actual lower edge. Opening the library defaults to `最近使ったもの` in both keyboard and Deck editing. A quiet bottom-right command clears only Recent and appears only while Recent is selected. A star on every draggable Action controls Favorites; only explicitly starred Actions appear there. Every successful concrete drop places that Action first in Recent. Both lists support shortcuts, text, applications/paths/URLs, macros, gestures, overlays, Deck actions, and other executable kinds; they persist independently without committing unrelated unsaved mapping drafts. The closed selector, popup categories, and Action rows retain their type-specific theme colors instead of forcing the accent color. Section headings live outside Action rows so hovering a row can never recolor a heading. The selector has no accent underline or detached extra enclosing surface; popup selection uses only a faint tint and check. The search field, category selector, custom shortcut creator, and Action cards share one right edge; the thin scrollbar occupies a separate eight-pixel gutter and must never cover a card or favorite star. The custom shortcut creator uses the same 58-pixel card size and visual language as Action rows. The far-right control is the favorite star, no six-dot drag glyph is shown, and the complete row remains draggable. Leaving the Deck editor for a keyboard or mouse layer closes the Action library; reopening it outside Deck must not retain the Deck-only monitor category.
- While an Action-library item is over an assignable key, the complete rounded key grows to `1.18x` around its center and stays above adjacent keys. The added overlap on each side remains below ten percent of that key's width, so neighboring keys cannot be hidden. The key presents label-only `TAP` and `HOLD` halves: both half surfaces remain transparent, a quiet divider preserves the one-piece rounded face, and only the selected label receives a bounded soft glow. The custom JIS Enter surface redraws its complete rounded L-shaped accent outline above those halves. An enlarged mouse key raises the complete opaque mouse host above its external group title, so the title can neither cover nor show through the key. Never restore full-half accent fills, square color cutouts, press icons, a missing Enter outline, or a drag preview that covers either label.
- A configured long action is shown on the normal one-piece key face only by a small bottom-right `HOLD` pill colored for the long Action; no black divider, bottom band, or hold icon is permitted. A long-only mapping keeps the key face neutral and colors only that `HOLD` pill; the key face receives an Action color only when TAP is configured. Assigned-key hover uses one rounded card with concise `TAP` and `HOLD` rows. Every executable Action kind must produce a non-empty friendly row, including shortcuts, overlay and Deck actions, keys, text, applications/paths/URLs, mouse actions, macros, profiles, gestures, and disabled actions; raw field labels such as `アクション：` and `実行内容：` are not shown. Configured TAP and HOLD summary cards are independent drag sources and each has a favorite star. A successful valid drop moves only that source slot and provides one undo transaction covering both source and overwritten destination; cancellation, an invalid destination, and the same source/destination slot never clear the source. Star clicks never arm a drag.
- Deck-button hover uses intent, not pointer transit: a brief crossing must leave every button at its normal scale. A settled pointer grows only that button slowly to `1.07x` with a non-overshooting curve; leaving returns it promptly to `1x`. The transform must never resize or move the hit surface, hide a neighboring button, or leave an animation clock or elevated stacking order behind after rapid travel.
- Selecting any entry in the Action category popup keeps the library open; this applies to every Action group and the Deck-only monitor group. Only a genuine blank editor click dismisses the library.
- Deck chrome opacity is independent from keypad opacity and ranges from 0 to 100 percent. It affects only the Deck background/chrome surface and gaps; Deck buttons, button content, title, grip, pin, maximize, close, and more controls stay fully opaque and theme-colored. At zero percent the Deck background and outer border are visually absent, leaving only buttons and header controls. The Deck has no visible outer border at any opacity. Slider movement updates only chrome alpha once per render frame, never rebuilds buttons, and Auto Save waits for release.
- Deck monitor controls keep slider/thumb mouse capture and cannot initiate panel movement. Monitor charts update from live shared samples, vary by metric, obey RELYR's Animation setting, and cannot add a top-level or hit-testable visual surface. A monitor cell constructs only the visualization required by its metric and routine selection/theme refreshes reuse that live view; sampling must not create an unbounded chain of animation clocks, subscriptions, or discarded graph trees.
- RELYR's Animation setting controls only visual glow, movement, and scaling. It must never change input routing, assignment behavior, Deck synchronization, persistence, or any overlay hit-test region. Before animating a transform obtained from a WPF template, clone any frozen transform and attach the mutable clone to the element. Every optional motion entry point must contain its own failure; a remaining animation-only dispatcher exception disables motion for the current process and is handled without shutting down the resident process, releasing input ownership, or changing the user's saved Animation setting. New configurations default both Animation and Auto Save to on; an explicitly saved off value remains off after upgrade.
- Opening the Action library is transactional. Build and validate its rows before replacing the inspector, tolerate malformed imported/runtime values with a safe icon or omission, and contain any remaining open-time exception inside that command. A failed Action-library open may report the error and restore the inspector, but must never terminate the resident process, release input ownership, or leave a half-visible pane.
- The top toolbar is a single non-wrapping row. At compact widths it may hide context labels, narrow the profile selector, and icon-compact multi-select, but it must keep profile creation, layout selection, multi-select copy/paste/delete, and Save visible, ordered, non-overlapping, and automation-named.
- Shutdown, helper exit, emergency release, and session transitions defensively emit mouse-button Up transitions for left, right, middle, Back, and Forward. This recovery cannot depend only on one process's generated-input tracking set.
- That unconditional recovery applies only after the process has actually started system input hooks. Self, UI, startup, shutdown, configuration, publish-probe, and other no-hook processes release only input tracked as generated by that process; they must never emit standalone Back/Forward `Up` events into the user's active browser session.
- Every Deck, keypad, preview, and drag path that takes WPF mouse capture releases it on normal Up, hide, close, cancellation, and failure. A cached hidden overlay must never retain mouse capture.
- Fullscreen overlay input consumption is transactional: any construction, show, or close failure clears `fullScreenActive`, `fullScreenClosing`, and dismissal state in a `finally` path. Invisible or failed fullscreen overlays must never consume input.
- A fullscreen bookkeeping flag alone never authorizes input suppression. Keyboard and mouse input may be consumed only while at least one owned native fullscreen HWND both exists and is visible; a missing or hidden native surface resets the transaction and fails open on that same physical event. Publish the active flag only after `Show` has produced a visible native surface. With no configured mapping or active layer, every virtual-key Down/Up pair passes to the next Windows hook.
- Closing the last fullscreen overlay through any path clears its input-consumption transaction and restores a visible system cursor. If the UI dispatcher cannot accept or execute the close request within the bounded watchdog interval, the cached native handles are hidden without touching WPF from the watchdog thread and the hook fails open instead of leaving a click-blocking wall.
- Coordinate capture is one-shot. Cancelling, closing, session transition, disposal, or a new physical Down after a missing Up clears its suppression state so a later ordinary click can never lose only its Up transition.
- Windows tray startup makes mappings, hooks, profile routing, Deck execution, and the elevated-helper connection available before constructing the keyboard and Deck editor visuals. Deferred editor initialization occurs once on first display and must not change the applied runtime profile or mappings.
- Only a production UI host may register the RELYR notification icon. Development, diagnostic, integration-test, and elevated-helper processes must never call the Shell notification-area add path. The production icon uses one permanent GUID so repeated upgrades cannot create duplicate RELYR rows in Windows notification settings.
- Do not replace the retained known-good installer until the candidate passes the required gates and the user has approved replacement. Record version and SHA-256 for every candidate supplied for user verification.
- An in-app update preserves the published GitHub Release body before launching the installer and displays it once, after the matching new version starts. Release-note state must not delay startup, erase settings, or repeat on later launches.
- GitHub Release naming is fixed and must not vary between releases. Use the title `RELYR v<version>` and the four filenames `RELYR-Setup-<version>.exe`, `RELYR-Setup-<version>.exe.sha256`, `RELYR-Update-<version>.exe`, and `RELYR-Update-<version>.exe.sha256`. Each GitHub asset display label must be exactly identical to its versioned filename; never replace it with a generic label or a Japanese translation. `<version>` must come from the current `RELYR.csproj`, never from a screenshot, example, previous Release, or manually remembered value. Keep the Release body in Japanese.
- Diagnostic and release builds are distinct. A diagnostic build must write logs to a user-writable path. User-environment confirmation of a diagnostic build is not, by itself, permission to call it a final release.
- Internal callbacks and mocked output prove only state-machine intent. They do not prove physical hook delivery, process-integrity routing, visible overlay behavior, persistence, or cross-process synchronization.

Before reporting completion, explicitly review this permanent regression set:

1. RELYR main window: standard, Space, CapsLock, MouseRight, MouseBack, and MouseForward layers remain active.
2. Ordinary applications: the same layers retain their existing behavior. In an input-disabled application, a missing Up from an unassigned OEM/IME key must never reactivate mappings or layers; leaving the application restores every layer immediately.
3. Normal left click is never assigned, replaced, or captured. `Taskbar+MouseLeft` TAP/HOLD are never assignable or intercepted, so Windows receives the original left-button sequence and pinned app icons remain draggable/reorderable. `Taskbar+MouseRight` TAP is never assignable or intercepted; a configured right-button HOLD preserves the Windows 11 app-icon right-click menu through the atomic replay worker. The worker waits for the physical hook callback to return, and queue completion cannot discard an already-suppressed restoration event. Ordinary right/back/forward clicks still replay correctly. Unassigned child clicks pass through held mouse layers even when the layer is released first. A mapped MouseRight wheel/tilt layer still permits native right-drag, and its generated Down is always followed by movement before any generated Up so it cannot become a context click. Direct `Taskbar+MouseMiddle` shortcuts execute without treating the taskbar as a cursor-target window, while taskbar shell surfaces remain rejected for window actions.
4. Profile auto-switching follows the foreground application only, remains stable, and does not change the editor dropdown unless the user selects it. Opening an owned RELYR management dialog must not preserve an unrelated application's runtime profile, and the dialog's title-bar close command remains usable.
5. Deck editor and live overlay synchronize in both directions without restart, including profile-linked layouts with different dimensions.
6. Tray restart preserves input ownership, profile state, mappings, and Deck synchronization.
7. Repeated actions and virtual-desktop changes do not leave captured keys/buttons, double-execute actions, or stop the hooks. Two gesture definitions may independently use different movement thresholds and keep the cursor fixed or allow it to move; an active gesture retains both values captured on its initial press.
8. Settings, mapping `Application` conditions, profiles, and Deck layouts are not erased, globally broadened, or silently migrated.

If a required item cannot be exercised safely in the current session, say so. Do not substitute an unrelated mocked test or claim that the item was verified.

## Hot-path rules

- A hook callback may do bounded dictionary/list lookups and small user32 queries. It must not enumerate windows, wait on a task, perform file/process I/O, call a dispatcher synchronously, or call `SendInput`.
- Capture the selected mapping once in `activeInputMappings`; all later gesture/long-press/drag decisions for that physical press reuse the snapshot.
- Query taskbar state only when a matching Taskbar mapping exists. Query foreground process only when a candidate has an application condition.
- Mouse-move profile checks are coalesced. When automatic routing is disabled and already settled, do not queue a dispatcher operation.

## Shutdown and process ownership

- Production has one elevated resident input owner protected by `RELYR.SingleInstance.v2`.
- Tray Exit, emergency stop, updates, and uninstall signal the path-specific shutdown event. The independent process watchdog is the final fallback for a blocked UI dispatcher.
- A normal launch that overlaps resident shutdown waits for the single-instance mutex to be released and then starts the replacement resident. A shutdown acknowledgement must never consume the replacement launch and leave RELYR with no resident process. Resident start and exit reasons are recorded in the bounded lifecycle log for evidence-backed diagnosis.
- Recovery may terminate only a process whose executable metadata identifies it as RELYR. Resolve its path with `PROCESS_QUERY_LIMITED_INFORMATION`; do not depend on `Process.MainModule`.
- Never kill child applications launched by mappings and never use a global image-name `taskkill` in the installer.

## Safe validation sequence

1. Run `powershell -ExecutionPolicy Bypass -File .\verify-source-safety.ps1`.
2. Build Release with warnings as errors into repository-root `.verification`.
3. Run `--self-test`, `--ui-test`, `--startup-test`, and `--shutdown-test` from the isolated build.
4. Do not run `--engine-test`, `--engine-test-no-real`, or `ModifierClickScenarioTest` in an active Windows session.
5. Only when a newer installer was explicitly requested: bump the project version, build in isolated staging, verify version and SHA-256, scan with Defender, then atomically replace the four files in `artifacts/production`.

`build-production.ps1` and `build-installer.ps1` skip input-engine tests by default and run the static safety gate. Do not turn an input-injecting test into a default build step.
